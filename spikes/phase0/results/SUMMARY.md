## Notes (written by hand after the run)

Counts and wall time. Web: 12 tries x 3 conditions x 15 blocks (scaled down from 20 tries to fit the budget). Cli: the full 20 tries x 3 x 15 blocks. Full run 23:46:35 to 00:20:06 = 33.5 min, plus about 8 min of calibration and smoke before it (about 42 min of benchmark in total). Conditions were interleaved within each try index in random order. Nothing was run in parallel; everything ran under `nice -n 19`.

Knob calibration (30-block long runs, `calibration.jsonl`). Web: scale 1.0 (A/A) -0.7% (s.e. 0.5%), scale 0.9669 +2.4% (s.e. 0.6%), scale 0.9459 +4.6% (s.e. 0.9%). Cli: A vs identical copy -2.1% (s.e. 1.4%), B3 +3.1% (1.4%), B5 +4.6% (1.2%). The 30-block runs cannot resolve the effect to better than about +-1%, so knobs were fixed from the work-fraction model (about 88% of a request is scalable CPU work) and the realised effect is taken from the main run: web 3% knob realised +2.4% (s.e. 0.33%), web 5% knob +4.5% (0.55%); cli 3% knob +2.5% (0.17%), cli 5% knob +4.6% (0.21%). So the "3%" arms are really about 2.5% faster, i.e. right at the Rule S minimum gain of 2.44%; the "5%" arms are about 4.5-4.6%. Treat the 3% rows as a test of a ~2.5% change.

Reading the keep rates. A/A false keeps: Rule S 0/36 (web) and 0/60 (cli) across all k, so with 95% confidence the false-keep rate is below about 8% (web) and 5% (cli); Rule N keeps 1-2/12 (web) and 0-2/20 (cli), i.e. roughly 5-15%, as expected for an uncorrected 95% interval over many tries; Rule R (raw) keeps 17-25% (web) and about 50% (cli) of changes that do nothing. Power: web Rule S keeps 5% speedups at 8/12 (k=5) and 12/12 (k>=10), 3% (~2.5% real) at 3/12, 6/12, 6/12. Cli Rule S needs k>=10 and is weak: 5% at 9/20 (k=10) and 13/20 (k=15), 3% at 1/20 and 4/20. At k=5 cli Rule S can never keep: with 5 independent units the 99.9% studentized bootstrap interval includes degenerate resamples (all draws the same block) which `stats.py` maps to +-1e12, hence the astronomical half-widths (they are not a measurement; treat as infinite). The web half-widths at k=15 (99.9%) are 1.4% (A/A) to 2.5% (3% arm), and the cli half-width is about 4%.

Anomalies. (1) The web target has heavy-tailed block noise: 23 of 540 blocks are more than 4 robust sd from the median, with a worst block 67% off, and 1.55% of individual requests exceed 1.5x their route median (host contention while the owner is on the PC, or WSL scheduling). Medians absorb most of it, but it inflates the across-try spread of A/A (s.e. of the mean A/A effect 1.2% across 12 tries), and the A/A web effect is +0.55% (not significantly different from 0) with median -0.45%. The web 3% arm therefore has a wide interval. (2) No meaningful drift: the baseline arm changed +0.17% per 10 tries (web) and -0.43% per 10 tries (cli). (3) A/A order effect is within noise (web -0.29% +-0.75%, cli +0.33% +-0.23%). (4) Server warm-up: 3 warm-up rounds per route per restart, no visible warm-up problem in the medians, but each server restart is a fresh process (random hash seed) which adds some between-block variance. (5) WSL load average stayed near 0.8 (web) and 1.0 (cli), i.e. only our own job; the Windows host load is not visible from WSL, so contention from games would appear only as noise and spikes, not in these numbers. (6) The `interval` fields for web are over 12 route items per try, whereas cli uses blocks, so web k only changes the item score (median of k blocks), not the unit count.
